# 2·4패널 기본 역할과 순차 검증 · 0.1.0 유지

- [x] 결정: 버전 변경 없이 개선·커밋·푸시. 2·4개 기본 역할 전체 배분, Cursor UI 선택 경고, 다중 디버깅·코드 검토의 결과 전달과 컨트롤 타워 최종 검토.
- [x] 구현: 구현 역할 단일 담당을 유지하고 검토·디버깅·테스트는 전 패널 기본 선택. 누락 UI는 가능한 한 Cursor 이외의 AI에 배분.
- [x] 로컬 검증: 실제 Node 실패→원래 담당 수정→재테스트→순차 OK, 2·4패널 UI와 Claude 컨트롤 타워 시뮬레이션.
- [x] 최종 검증: Windows 포터블·Mac 두 CPU 패키지·CI 결과와 양쪽 원격 반영을 확인.

```gherkin
Feature: 전체 기능을 포함하는 기본 역할
  Scenario Outline: 패널 개수 변경
    When 패널을 <count>개로 선택한다
    Then 기능 구현과 UI 구현은 각각 한 담당에 배정된다
    And 디버깅과 코드 검토와 테스트 설계·실행은 모든 패널에 체크된다
    And 컨트롤 타워는 첫 패널에 고정되고 공급자는 사용자가 선택한다
    Examples:
      | count |
      | 2 |
      | 4 |
  Scenario: Cursor UI 직접 선택
    When Cursor의 UI 역할을 체크하거나 UI 담당의 공급자를 Cursor로 바꾼다
    Then 기본 취소인 네이티브 경고를 띄운다
    And 취소하면 체크 또는 공급자 변경을 되돌린다
    And 이 동의가 실제 코드 실행의 기존 승인을 대신하지 않는다
Feature: 순차 검증
  Scenario: 여러 AI의 확인
    Given 현재 파일 버전의 테스트 결과가 있다
    When 디버깅·코드 검토를 수행한다
    Then Grok·Cursor 다음 Gemini 다음 Claude 다음 GPT 순으로 검토하되 컨트롤 타워는 마지막이다
    And 선택한 담당만 참여하고 같은 공급자도 패널 ID를 구분한다
    And 다음 AI는 모든 현재 테스트 결과와 앞선 검토 의견을 받는다
  Scenario: 수정 필요 또는 테스트 실패
    When 한 검토에서 문제가 발견된다
    Then 다음 검토를 보류하고 원래 담당에게 수정을 전달한다
    And 원래 테스트와 완료 기준을 유지하며 재테스트한다
    And 새 파일 버전으로 검토를 다시 시작한다
    And 미실행 테스트와 일부 OK만으로 완료 처리하지 않는다
```

위험 파일 변경의 적용 전 교차 승인은 별도 안전 단계로 유지한다. 일반 구현은 독립된 파일·의존 관계 범위에서 병행할 수 있지만, 여러 디버깅 코드 변경 작업과 테스트 후 검토는 명시한 순서를 따른다. 순서와 전달은 호스트가 강제하고 AI의 요약만으로 테스트 통과를 만들어내지 않는다. 모델이 모든 버그를 발견한다고 보장하지 않는다. 실제 공급자 변경이나 한도 소진 시 기존 승인·대체 AI 정책도 유지한다.
